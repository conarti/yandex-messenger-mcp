### Почему 18%, а не 17% и не 12%
Scope вырос примерно вдвое (11 пунктов + auth UX → плюс 4 мутации-близнеца, отправка вложений,
3 долга доказательств, опросы + self-чат). Ambiguity при этом почти не сдвинулась, и это честный итог,
а не подгонка:

- **Вниз тянет** (новая неопределённость): формы `Vote`, `Pin`, `ReadMarker`/`SeenMarker` и правки
  (`convertMessageToPlain`) взяты **только из доки**, живьём не наблюдались. Дока по этому протоколу
  ошибалась многократно (§17: `Type:"👍"`, `Mode`-дискриминатор, шаблон `fileDownloadUrl`, пагинация
  search). Какой именно из трёх маркеров прочтения (`SeenMarker` / `UnseenMarker` / `ReadMarker`)
  соответствует «отметить прочитанным» в вебе - **неизвестно**. Семантика `Pin.Timestamp?` (пустой =
  открепить?) - **неизвестна**. Единица и обязательность полей `Vote.Choices` - **неизвестны**.
- **Вверх тянет** (снятая неопределённость): весь новый scope пришёл **с уже принятыми решениями**
  (confirm-политика с обоснованием, поведение с неизвестным типом реакции, валидация на запись);
  спайк 5 закрыл открытый вопрос про `int → emoji` фактом, а не гипотезой; upload-флоу описан
  пошагово (§12.1) и укладывается в известный `file_info.id`; долги доказательств - это не
  неизвестность в требованиях, а **известный список известных дыр**, каждая с готовым критерием проверки.
- **Итог:** +1 п.п. Удвоение scope стоило ровно одного пункта, потому что добавляли решённое,
  а не открытое. Ниже 0.2 порога, но запас сократился - формулировать AC для мутаций с доко-выведенными
  формами надо через живую проверку, а не через «как написано».

## Ключевой вывод разведки

**~10 из 11 запрошенных пунктов уже есть в протоколе — v1 их просто не выставляет наружу.** Это не реверс нового API, а «перестать выбрасывать то, что уже приходит». Карта:

| Запрос пользователя | Что уже в протоколе |
|---|---|
| Реакции + кто прочитал и когда | `list_reactions` — **но НЕ одним вызовом** (§14.3 врала, опровергнуто спайком 4, см. §17.12): `Mode` это дискриминатор, дефолт → `UserReactions`, `Mode:1` → `UserReads`. **Два вызова на сообщение.** Сиблинги §11.2 обрезаны и источником истины быть не могут |
| get_message по ID | `message_info {ChatId, Timestamp, InviteHash}` (§14.3) → `{Message, MyReactions}` |
| Упоминания без имён | `MentionedUsers[UserInfo]` — сиблинг `ClientMessage` (§11.2), лежит рядом с `MentionedUserIds[guid]` (§11.1). Имена УЖЕ приходят, v1 их выбрасывает |
| Пересылка: автор/чат/дата/текст оригинала | `ForwardedMessageRefs[{ChatId,Timestamp}]` (§11.1) + сиблинг `ForwardedMessages[...]` (§11.2) |
| reply_to | Reply моделируется как форвард с цитатой: `ForwardedMessageRefs` + `ForwardedMessageStyles.Quote` (§11.1, §11.2 — отдельного `Reply` в протоколе НЕТ) |
| Треды: чтение | `history` c `Threads:true`, `ChatIds`, `MessageDataFilter.DropThreadParentMessage` (§2.4/§14.2); `ThreadState{LastSeqNo, MentionTsMcs, HistoryStartTsMcs}` в `ServerMessageInfo` (§9.1) |
| Треды: вступление/выход | `join_to_thread {thread_id}` / `leave_thread {thread_id}` (§10, HTTP) |
| Удаление своего сообщения | `push({Plain:{ChatId, Timestamp}})` — пустой Plain (§9.3). Детект удаления при чтении: `ServerMessageInfo.Deleted=true` (§9.1) |
| Фильтр по датам | `MinTimestamp`/`MaxTimestamp` уже есть в `history` (§2.4/§14.2). v1 не выставляет их как даты. **`MaxTimestamp` — исключающая граница** (проверено живьём в v1, см. research §17) |
| Контекст вокруг сообщения | Комбинация `MinTimestamp`/`MaxTimestamp`/`Offset`/`Limit` вокруг метки |

**Единственный пункт, которого в протоколе НЕТ:** структурированное форматирование. `Text` = `{MessageText, Card?}` (§11.1), никаких entities/ranges. Совпадения по слову «entities» в доке — это про `search`, другое значение.

⚠️ Дока уже многократно ошибалась (см. research §17: гостевые артефакты, пагинация search, шаблон URL вложений, `Limit:0` vs `Limit:1`). Поэтому **каждый пункт таблицы подлежит живой проверке**, а не приёму на веру.

## Goal
Довести MCP до рабочего паритета с веб-интерфейсом по чтению и мутациям: сообщение должно приезжать со всем контекстом, который видит человек (реакции, кто и когда прочитал, связи, оригинал пересылки, имена упоминаний), любое сообщение должно доставаться по ID/ссылке вместе с окружением, треды должны работать как в вебе (включая создание), история фильтроваться по датам.

**Плюс симметрия чтения и письма:** на всё, что MCP умеет прочитать, он должен уметь ответить тем же способом, что человек в вебе - поставить и снять реакцию, поправить своё сообщение, удалить своё сообщение, отметить чат прочитанным, закрепить сообщение, проголосовать в опросе, отправить файл или картинку. Self-чат («Избранное») адресуется по имени, а не только литеральным ChatId.

**И честность доказательств:** места, где v2 держится на фикстурах или реконструкции (voice/gallery-вложения, форма push-ответа кроме `Status`, ресайз превью), закрываются живыми прогонами, а не остаются в README как долг.

## Constraints
- **Наблюдение важнее доки.** Каждый пункт карты выше проверяется живьём. При расхождении верна живая сессия, дока правится (research §17 — прецедент).
- **Треды: полный паритет** (решение Round 4). Включает создание треда кнопкой «Обсудить». **Спайк 1 закрыт: реверса не требуется** — создание это строковая деривация `thread_id` из `ChatId`+`Timestamp` плюс обычный `push` (тред = чат). Контра-довод Round 4 («реверс утянет релиз») оказался основан на ложной посылке: механики в доке не было, но в бандле она тривиальна. Цена паритета near-zero.
- **Форматирование: сырая строка** (решение Round 3, **спайк 2 подтвердил живьём**: entities на проводе НЕТ, `Text` = ровно `{MessageText}`, посланное вернулось байт-в-байт). Отдаём `MessageText` как есть и честно пишем в README, что форматирование это markdown внутри текста. **Структуру НЕ выдумывать**, client-side парсинг markdown в ranges отклонён.
- **`delete_message`: двухшаговый draft→confirm** (решение Round 5), единообразно с `send_message`. Draft показывает, что именно удаляется (чат, автор, время, текст), confirm-токен несёт ChatId+Timestamp. Удаление чужого сообщения отклоняет сервер — своё ограничение не изобретаем, но ошибку маппим внятно.
- **Всё вместе, одним релизом** (решение Round 4) — не разбивать на волны.

### Confirm-политика: draft→confirm ТОЛЬКО у необратимых (решение Round 7)

Критерий один: **можно ли откатить последствие тем же инструментом за один вызов**. Если да, confirm - это налог на каждое действие без выигрыша в безопасности. Если нет, цена ошибки платится один раз и навсегда.

| Инструмент | Confirm | Почему |
|---|---|---|
| `send_message` | **да** (уже есть) | Отправленное видят все; отзыв - отдельное действие с отдельной меткой «удалено» |
| `delete_message` | **да** (Round 5) | Необратимо. Текст не восстановить ничем |
| **отправка вложений** | **да** | Тот же класс, что `send_message`, плюс **необратимая заливка байтов на чужой диск** до всякой отправки. Draft обязан показывать имя, размер, тип и чат назначения |
| **правка своего сообщения** | **да** | **Перезаписывает текст**: прежняя редакция для нас потеряна (`edit_history` §14.3 живьём не проверялся, полагаться на него как на «отмену» нельзя). Draft показывает «было → станет» |
| **голос в опросе** | **да** | Голос виден всем участникам; отзыв голоса в протоколе **не обнаружен** - `Vote` (§9.3/§11.4) несёт `Choices[]`, механики снятия нет. Считаем необратимым, пока не доказано обратное |
| **реакции (поставить/снять)** | **нет** | Тривиально откатывается тем же инструментом: `Reaction.Action:REMOVE=1` (§9.3). Ошибка живёт секунды и стоит один вызов |
| **закреп/открепить** | **нет** | Легко снять, `Pin` (§9.3/§11.4). Ничего не разрушает |
| **отметка прочтения** | **нет** | Безобидна: сообщает факт, который и так наступил (сообщение прочитано агентом). Ничего не создаёт и не разрушает |

**Обоснование асимметрии:** confirm существует, чтобы человек успел остановить необратимое, а не чтобы подтверждать каждое касание. Раздача confirm обратимым мутациям обучает пользователя жать confirm не глядя - и тогда он прожмёт его и на `delete_message`. Дешёвый confirm обесценивает дорогой.

### Реакции: факты спайка 5 (обязательны к исполнению)

- **Таблицы `int → emoji` НЕ СУЩЕСТВУЕТ by design.** Эмодзи-литералов в бандле **0** по всем 15 чанкам. Реакция - это **PNG-артворк, который сервер отдаёт по id**: `https://files.messenger.yandex.net/reactions/{type}/{size}`. Набор пикера приходит из `https://tools.messenger.yandex.net/config.json` и **зависит от namespace чата** - единого набора нет.
- **Карта: `.omc/spikes/yandex-mcp/v2/reaction-map.json`, 52 записи.** 6 доказаны живым кликом (👍→100102, 👎→100103, ❤️→100109, 👀→100110, 💯→100131, 🔥→100104), остальное - из ассетов и визуального прочтения пикера. **Колонка `emoji` - наша аппроксимация артворка.** Авторитетны `name` (имя ассета с сервера) и сам артворк; выдавать аппроксимацию за «эмодзи от Яндекса» нельзя.
- **Сервер `Type` НЕ валидирует вообще:** `999999` → `Status:1`, читается обратно дословно. **Вывод спайка 4 про `Type:1` был неверен**: `1` прошёл не потому, что `1` = 👍, а потому, что валидации нет. **`1` - мусор, в карту не вносить.**
- **Поведение на чтение:** `type` отдавать **ВСЕГДА** (это единственное, что реально пришло с провода; `name`/`emoji` - наша интерпретация). Неизвестный тип → `{type:N, emoji:null, name:null, unknown:true}`. **`chr(type)` не подставлять** (`100102` → `𘜆`, тангутский иероглиф). Карта - lookup с фолбэком, не `switch`, который бросает: неизвестный тип это штатный сценарий, ронять `get_message` из-за реакции нельзя. Молча глотать неизвестную реакцию тоже нельзя - `Count` не сойдётся с суммой показанного.
- **Поведение на запись: валидировать по карте ДО отправки.** Это единственное место, где строгость нужна: сервер не защитит, он молча запишет мусор, и **его увидят все участники чата**. Официальный веб на неизвестном типе рисует битую картинку (`404`, `naturalWidth:0`) - фолбэка нет даже у Яндекса.
- **Правило «type = Unicode-кодпоинт» верно ровно для 10 legacy-записей и НЕ обобщается.** Свип по ~50 популярным кодпоинтам дал 404 на всех, кроме этих десяти. Legacy-типы рабочие, но вне пикера.
- **`Limit` в `list_reactions` обязателен**: `{ChatId, Timestamp}` без `Limit` → `BACKEND_CALL_ERROR(2)`. Спайк 4 этого не заметил; «`Mode:3` → ошибка» из спайка 4 подлежит перепроверке **с `Limit`**.
- **`Reaction` уходит внутри полного конверта `ClientMessage`** (`buildPushParams`: `ClientTransportId` + `UserAgent` + `Meta.Origin` + `ClientSupportedFeatures`). Плоский `push({Reaction:{...}})` даёт ложный `Status:4 NO_SUCH_CHAT` - легко принять за неверный `ChatId`.
- **Имя `ALL:2` в енуме `ListReactionsMode` врёт**: живьём `Mode:2` отдаёт только `UserReactions`. Верить наблюдению, не имени.
- **Кастомных реакций нет**, но пространство типов **открыто** (доказано `999999`). «Набор закрыт» - свойство UI, а не сервера.

### Отправка вложений: флоу и границы

- **3 шага (§12.1, способ A - Disk):** `upload_to_disk {files:[{name, upload_id(uuid), size, chat_id}]}` → `{files:[{upload_url}]}`; затем **HTTP PUT сырых байт** на `upload_url` → заголовок **`Location`**; затем `add_files {chatId, files:[{location}]}` → `{file_id}`. Дальше - **обычное сообщение** с `file_info.id = fileId`. Отдельного «send file» в протоколе нет.
- Исходящие payload по типам (§12.1): image `{width, height, preview_url, ..., file_info}`; file `{file:{file_info, previewHint?}}`. Voice/gallery в scope отправки **не входят** (см. Non-Goals) - для них закрывается только долг **чтения**.
- Известные ошибки шага 1: **507/403 - квота, 413 - размер**. Маппить внятно, а не «upload failed».
- ⚠️ Форма ответа на `push` живьём подтверждена **только по ключу `Status`** (долг доказательств). До закрытия долга: **ответ без числового `Status` трактуется как отказ**, а не как тихий успех - инвариант v1 сохраняется и для вложений.

### Долги доказательств: что именно считается закрытием

Долг закрывается **живым прогоном**, а не рассуждением. Не закрылся - остаётся в README дословно, с указанием, что именно пробовали.

- **voice/gallery-вложения** (сейчас только фикстуры): прочитать **реальное** голосовое и реальную галерею с живого аккаунта. Если на профиле их нет - долг остаётся долгом, фикстуру за доказательство не выдавать.
- **Форма push-ответа кроме `Status`** (сейчас реконструкция по маппингу веб-клиента): подтвердить на проводе имена `MessageInfo`/`PrevTimestampMcs`/`RateLimit.WaitFor`. Заодно - **единица `rate_limit.wait_for`** (сейчас неизвестна; сырое значение трактуется как мс и зажимается в 1-60 с). `rate_limit` на успешной отправке не приходит вовсе, так что случай нужно ловить.
- **Превью `?size=`** (сейчас: `MIDDLE2048` вернул **байт-в-байт оригинал**, 294561 байт): проверить на картинке, **заведомо большей кэпа**. Исход «ресайз не работает / параметр игнорируется» - тоже закрытие долга, если он доказан.

### Опросы и self-чат

- **Опросы: читать и голосовать.** Чтение - `poll_info {ChatId, Timestamp, Limit:50, ReturnResults:true}` → `{answerVotes, myChoices, results}` (§14.3). Голос - `push({Vote:{ChatId, Timestamp, Choices[], Results}})` (§9.3/§11.4). ⚠️ Обе формы **из доки, живьём не наблюдались**. Механика **снятия/смены голоса в протоколе не обнаружена** - отсюда confirm.
- **Self-чат («Избранное») адресуем по имени.** Сейчас резолв по построению отбрасывает самого пользователя как собеседника, и «Избранное» достижимо только литеральным `ChatId`. Гейт self-чата известен из спайка 5: `ChatId === <guid>_<guid>` + `PrivateChatInfo` + `PartnerInfo.Guid === myGuid`.
- Сохранить инварианты v1: stdout под MCP stdio (логи в stderr), редакция секретов и текста в логах, никаких живых uid/guid/cookie в репо, приватность в тестах (фикстуры синтетические).
- Курсоры и метки времени — string/BigInt, не float (§14.2, инвариант v1).
- Даты в фильтрах принимать в человеческом виде (ISO) и конвертировать в мкс; помнить, что **`MaxTimestamp` исключающая**.

## Non-Goals (v2)
- **Real-time / live-события / бот**: подписки на новые сообщения, typing, seen, presence. Пользователь явно просил **оставить отложенным**. Инструмент отвечает на запрос, а не слушает поток.
- **Звонки и встречи** (Telemost, `CallingMessage`/`MeetingCallingMessage` §11.4).
- **Управление чатами**: создание, участники, роли, инвайты (§10 «Chat mutations»).
- **Мульти-аккаунт.**
- **OAuth без браузера.** В бандле это другой транспорт с другим форматом кадров, а не «второй режим»; потребует отдельного WS-клиента. Остаётся cookie-авторизация.
- **Client-side парсинг markdown в entities** (явно отклонён в Round 3, подтверждён спайком 2: entities на проводе нет).

**Переехало из Non-Goals в scope (Round 6):** ставить реакции, править своё сообщение, отправка файлов/картинок, read-маркеры, закреп, опросы. В v2 это **активный scope**, а не отложенное.

**Осталось за бортом внутри взятого scope** (уточнения, чтобы не расползлось):
- Отправка **voice/gallery** (только чтение; отправка - image и file).
- Правка **чужих** сообщений, снятие **чужих** реакций - отклоняет сервер, своё ограничение не изобретаем.
- Очистка истории (`ClearUserHistory`), важность (`UpdateFields.ImportanceFlag`), жалобы (`Report`) - не запрашивались.

## Acceptance Criteria
- [ ] `get_history` возвращает у сообщения: реакции (emoji, count, список пользователей, время реакции конкретного пользователя), прочтения (кто, когда), `reply_to`, признак пересылки, корень треда — если API это отдаёт. Проверяемо на **сообщении `1784287503814009`**, где v1 вернул только автора/текст/время/базовые флаги.
- [ ] Реакции и прочтения достаются **двумя вызовами `list_reactions`**: дефолтный `Mode` → `UserReactions`, **`Mode:1` → `UserReads`+`ReadsCount`** (вместе не приходят, §17.12). Сиблинги `history` НЕ использовать как источник истины — они обрезаны (`ReadsCount:10` при `RecentUserReads` длиной 3). Отсутствие `UserReads` отдавать как «не отслеживается», НЕ как ноль.
- [ ] `Reaction.Type` трактуется как **int - id артворка** (§17.12 + спайк 5), не emoji и не кодпоинт. Известный тип → `{type, name, emoji, count}`; **неизвестный → `{type:N, name:null, emoji:null, unknown:true}`**, без `chr(type)` и без молчаливого проглатывания. `type` присутствует **всегда**. Проверяемо: подставить в карту-фолбэк тип `999999` - `get_message` не падает, реакция видна как unknown, `Count` сходится.
- [ ] `list_reactions` вызывается **с обязательным `Limit`**; вызов без `Limit` (регресс-тест на форму запроса) не собирается или явно отвергается на входе, а не улетает в `BACKEND_CALL_ERROR(2)`.
- [ ] Для пересланного сообщения возвращаются исходный автор, исходный чат, дата и текст/вложения оригинала.
- [ ] Упоминания резолвятся в имена (`MentionedUsers`), а не остаются `@<guid>`. При отсутствии имени — явно `unresolved`, не молча guid.
- [ ] `get_message(chat_id + message_id)` возвращает одно сообщение без загрузки истории (через `message_info`).
- [ ] `get_message` принимает URL вида `https://yandex.ru/chat/#/join/.../<message_id>` и резолвит его в чат+сообщение (§17.11: <message_id> в хвосте = Timestamp; hash = invite_hash; резолв через get_chats_info {invite_hash} без CSRF).
- [ ] `get_message_context(message, before, after)` возвращает N сообщений до и после указанного.
- [ ] `get_history` принимает `from_date`/`to_date`/`after` (ISO), корректно транслируя в `MinTimestamp`/`MaxTimestamp` с учётом исключающей верхней границы. Проверяемо: «сообщения за сегодня» одним вызовом.
- [ ] Треды: `get_thread(message|thread_id)` отдаёт сообщения треда отдельно; сообщение несёт признак «есть тред» и корень; отправка в тред работает через draft→confirm; **создание треда из сообщения («Обсудить») работает** (§17.10: деривация thread_id + первый push материализует тред); join/leave через `join_to_thread`/`leave_thread`.
- [ ] `delete_message(chat_id, message_id)`: draft показывает удаляемое и НЕ удаляет; confirm удаляет; удалённое сообщение при повторном чтении приходит с `Deleted=true`.
- [ ] Форматирование: `MessageText` отдаётся сырым; README честно фиксирует, что структурированных entities протокол не даёт (либо, если спайк их найдёт, они выставлены).
- [ ] First-run auth: вызов инструмента при отсутствии сессии не приводит к молчаливому таймауту. README фиксирует требование к таймауту MCP-клиента (≥5 мин), т.к. ожидание логина дольше дефолтов.
- [ ] Регрессия v1 зелёная: build/typecheck 0, весь существующий набор тестов проходит.

### Мутации-близнецы

- [ ] `set_reaction(chat_id, message_id, type)` ставит реакцию **одним вызовом, без confirm**; `list_reactions` после этого возвращает поставленный тип. `Action:REMOVE=1` снимает её тем же инструментом одним вызовом. Проверяемо живьём **в self-чате**.
- [ ] `set_reaction` **валидирует `type` по карте ДО отправки**: тип вне `reaction-map.json` отвергается клиентом. Проверяемо: `999999` и `1` не уходят на провод (сервер бы их принял - `Status:1`).
- [ ] `Reaction` уходит **полным конвертом `ClientMessage`**. Регресс-тест на форму запроса: плоский `push({Reaction:{...}})` не собирается. (Симптом ошибки - ложный `NO_SUCH_CHAT`, а не «неверный тип».)
- [ ] `edit_message(chat_id, message_id, new_text)`: **draft показывает «было → станет»** и НЕ правит; confirm правит. После правки сообщение читается с новым текстом и **непустым `LastEditTimestamp`**. Правка чужого - внятная ошибка от сервера, не своя выдумка.
- [ ] `mark_read(chat_id, ...)` отмечает прочитанным **одним вызовом, без confirm**. Проверяемо: непрочитанное (`LastSeqNo - LastSeenByMeSeqNo` > 0, §17.9) после вызова обнуляется. **Какой из `SeenMarker`/`UnseenMarker`/`ReadMarker` соответствует вебу - установить живым прогоном**, в спеке это неизвестно.
- [ ] `pin_message(chat_id, message_id)` закрепляет **одним вызовом, без confirm**; открепление работает тем же инструментом. **Семантика `Pin.Timestamp?` (пустой = открепить?) - неизвестна, установить живьём.**

### Отправка вложений

- [ ] `send_file(chat_id, path)` и отправка картинки проходят **все 3 шага** (`upload_to_disk` → PUT сырых байт → `add_files`) и **draft→confirm**. Draft показывает имя, размер, тип, чат назначения и НЕ заливает байты. Отправленное читается обратно с `file_info.id` и скачивается.
- [ ] Ошибки upload маппятся раздельно: **507/403 → квота, 413 → размер**. Не «upload failed».
- [ ] Ответ без числового `Status` трактуется как **отказ**, а не тихий успех (инвариант v1 распространён на вложения).

### Долги доказательств (критерии живой проверки)

- [ ] **voice/gallery прочитаны живьём** с реального аккаунта, не из фикстур. Если на профиле их нет - в README остаётся долг с указанием, что искали и не нашли; фикстура доказательством не объявляется.
- [ ] **Форма push-ответа подтверждена на проводе** сверх `Status`: имена `MessageInfo`/`PrevTimestampMcs`/`RateLimit.WaitFor` наблюдались, либо долг остаётся дословно. Отдельно: **пойман живой `rate_limit`** и определена **единица `wait_for`** (сейчас неизвестна, кламп 1-60 с). Не поймали - кламп и запись сырого значения в лог остаются.
- [ ] **Превью `?size=` проверено на картинке заведомо больше кэпа.** Результат зафиксирован фактом: ресайз работает / параметр игнорируется / поведение иное. «Вернулся байт-в-байт оригинал» без контроля размера исходника доказательством не считается.

### Опросы и self-чат

- [ ] Опрос читается: `poll_info` отдаёт варианты, результаты и мой выбор (`answerVotes`/`myChoices`/`results`); в выдаче сообщения виден признак «это опрос». **Формы из доки живьём не проверялись** - расхождение фиксируется правкой доки (§17-прецедент), а не подгонкой под доку.
- [ ] `vote_in_poll(chat_id, message_id, choices)` голосует **через draft→confirm**; после confirm `poll_info` показывает мой голос в `myChoices`. Если живой прогон обнаружит механику снятия/смены голоса - **confirm пересматривается** (основание для него отпадает).
- [ ] Self-чат («Избранное») **резолвится по имени**, а не только литеральным `ChatId`. Проверяемо: `get_history` по имени «Избранное» отдаёт self-чат. Резолв больше не выбрасывает самого пользователя как собеседника (гейт: `ChatId === <guid>_<guid>` + `PrivateChatInfo` + `PartnerInfo.Guid === myGuid`).

### Confirm-политика (сквозной критерий)

- [ ] Confirm есть **ровно** у: `send_message`, `delete_message`, отправки вложений, правки своего сообщения, голоса в опросе.
- [ ] Confirm **отсутствует** у: реакций (поставить/снять), закрепа/открепа, отметки прочтения - они выполняются одним вызовом. Проверяемо: тест на список инструментов, требующих confirm-токен, совпадает с этими двумя перечнями.
